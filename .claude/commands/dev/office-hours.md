# /office-hours - 제품 판단 (Think 단계)

기능 구현 전에 "이것을 만들어야 하는가?"를 검증하는 제품 전략 판단 프로세스.

코드를 작성하기 전에 이 프로세스를 통해 만들 가치가 있는지 판단한다. Palantir FDE 방식의 문제 분해를 통해 비즈니스 임팩트 중심으로 Go / No-Go / Pivot을 결정한다.

## /office-hours vs /brainstorm

| 항목          | /office-hours                  | /brainstorm                    |
| ------------- | ------------------------------ | ------------------------------ |
| **핵심 질문** | "이것을 만들어야 하는가?"      | "이것을 어떻게 만들 것인가?"   |
| **관점**      | 비즈니스 임팩트, 사용자 가치   | 기술 설계, 아키텍처            |
| **출력**      | Go / No-Go / Pivot 판단 보고서 | 설계 문서 (`docs/plans/`)      |
| **순서**      | 가장 먼저 (Think 단계)         | /office-hours 다음 (Plan 단계) |

## 사용법

```
/office-hours 멀티플레이어 기능
/office-hours 게임 추천 시스템
/office-hours 업적/도전과제 시스템
/office-hours 게임 내 채팅 기능
/office-hours 게임 리플레이 저장
```

## 핵심 원칙

- 판단이 나기 전까지 **코드 작성 금지** — 설계도 하지 않는다
- **"만들 수 있는가"보다 "만들어야 하는가"** 를 먼저 묻는다
- 지표 없는 판단 금지 — "좋을 것 같다"는 근거가 아니다
- 경쟁사 맹목적 복제 금지 — Game Park의 맥락에서 재평가한다
- **YAGNI** — "있으면 좋겠다"는 제거 대상이다

## 프로세스

`product-advisor` 서브에이전트를 호출하여 아래 단계를 수행한다.

### 1단계: 문제 정의 (Problem Definition)

사용자에게 질문하며 문제를 명확히 한다:

- **어떤 사용자 문제를 해결하는가?** — 한 문장으로 정의
- **문제의 빈도는?** — 매일 / 매주 / 가끔 / 거의 없음
- **문제의 심각도는?** — 플랫폼 이탈 유발 / 불편함 / 사소함
- **누구의 문제인가?** — 신규 유저 / 재방문 유저 / 게임 개발자 / 운영자
- **현재 사용자는 이 문제를 어떻게 해결하고 있는가?** — 대안이 있다면 빌드 우선순위 하락

### 2단계: 임팩트 분석 (Impact Analysis)

게임 플랫폼 핵심 지표 기준으로 평가한다:

- **사용자 리텐션** — 7일/30일 재방문율에 기여하는가?
- **DAU** — 일일 활성 사용자 수에 직접 기여하는가?
- **플레이 타임** — 세션당 평균 플레이 시간을 늘리는가?
- **게임 다양성** — 새로운 게임 등록/발견을 촉진하는가?
- **만들지 않으면 어떻게 되는가?** — 아무 일도 안 일어나면 No-Go 시그널
- **이 기능 없이 성장할 수 있는가?** — Yes라면 우선순위 재검토

### 3단계: 경쟁 분석 (Competitive Analysis)

WebSearch를 활용하여 유사 플랫폼(itch.io, CrazyGames, Poki)의 현황을 조사한다:

- 경쟁 플랫폼이 이 기능을 이미 제공하는가?
- 제공한다면 효과가 있는가? 제공하지 않는다면 의도적인가?
- Game Park의 차별화 포인트가 될 수 있는가?

### 4단계: 스코프 최소화 (Scope Minimization)

- **MVP 정의** — 핵심 가치를 전달하는 최소 기능만 정의
- **1주 스코프** — 1주 안에 구현 가능한 범위로 축소. 불가능하면 분할
- **기존 코드 활용** — 코드베이스 조사로 재사용 가능한 컴포넌트/로직 확인

### 5단계: 판단 (Judgment)

세 가지 중 하나를 결정한다:

- **Go** — 문제가 명확하고, 핵심 지표에 기여하며, 1주 내 MVP 가능 → `/brainstorm`으로 이어진다
- **No-Go** — 문제가 불명확하거나, 지표 기여가 없거나, ROI가 낮음 → 중단 사유와 대안 제시
- **Pivot** — 문제는 유효하지만 해결책이 최선이 아님 → 대안 접근법과 피벗된 MVP 제시

## Go 판단 이후

Go 판단이 나오면 자연스럽게 `/brainstorm`으로 연결한다:

```
/office-hours 업적 시스템  →  Go 판단  →  /brainstorm 업적 시스템
```

판단 보고서의 MVP 정의와 성공 지표를 `/brainstorm` 설계의 입력으로 활용한다.

## 언제 사용하는가

- **새로운 기능**을 제안받았을 때 — "이거 만들어 주세요"
- **큰 방향 전환**이 필요할 때 — "플랫폼 구조를 바꾸고 싶어요"
- **사용자 요청**이 들어왔을 때 — "이런 기능이 있으면 좋겠어요"
- **경쟁사에서 본 기능**을 도입하고 싶을 때 — "itch.io에 이런 게 있던데"
- **리소스 투입 판단**이 필요할 때 — "이걸 만들 여유가 있는가?"

## 언제 건너뛰는가

아래의 경우 `/office-hours` 없이 바로 작업해도 된다:

- **버그 수정** — 이미 있는 기능이 오작동하는 경우
- **사소한 개선** — 버튼 텍스트 변경, 스타일 미세 조정 등
- **인프라/설정 변경** — ESLint 규칙 추가, 패키지 업데이트, CI 수정 등
- **문서 작업** — README, 가이드, 주석 추가 등
- **리팩터링** — 기능 변경 없이 코드 품질만 개선하는 경우

## 주의사항

- "기술적으로 재미있어서"는 빌드 이유가 아니다. 사용자 가치가 먼저다.
- 이미 투자한 시간 때문에 잘못된 방향을 계속하지 않는다. 언제든 No-Go 할 수 있다.
- 사용자가 이미 명확한 근거를 가지고 있다면 분석 단계를 줄여도 된다.
