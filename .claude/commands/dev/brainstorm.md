# /brainstorm - 아이디어 브레인스토밍

기능 구현 전에 아이디어를 탐색하고 설계를 확정하는 협업 프로세스.

코드를 작성하기 전에 이 프로세스를 통해 무엇을 만들지 명확히 한다.

## 사용법

```
/brainstorm 장바구니 기능
/brainstorm 실시간 알림 시스템
/brainstorm 검색 필터 개선
```

## 핵심 원칙

- 설계가 승인되기 전까지 **코드 작성 금지**
- 질문은 **한 번에 하나씩** — 여러 질문을 한꺼번에 하지 않는다
- 가능하면 **객관식** 형태로 질문한다 (AskUserQuestion 도구 활용)
- **YAGNI** — 불필요한 기능은 설계에서 제거한다
- **2-3가지 접근법**을 항상 제시하고 비교한다

## 프로세스

아래 단계를 순서대로 진행한다. 각 단계를 TaskCreate로 태스크로 등록하고 진행 상황을 추적한다.

### 1단계: 프로젝트 컨텍스트 파악

- 관련 파일, 디렉토리 구조 탐색
- 최근 커밋 히스토리 확인
- 기존에 관련된 컴포넌트/훅/유틸이 있는지 확인
- `@/components/ui` 및 `@doubltworks/` 패키지에서 사용 가능한 것 확인

### 2단계: 요구사항 질문

사용자에게 **한 번에 하나씩** 질문하며 아이디어를 구체화한다:

- 이 기능의 **목적**은 무엇인가?
- **사용자 시나리오**는 어떻게 되는가?
- **제약 조건**이 있는가? (성능, 접근성, 디바이스 등)
- **성공 기준**은 무엇인가?
- 기존 기능과의 **연관성**은?

> AskUserQuestion 도구를 적극 활용한다. 선택지를 제공하면 사용자가 답하기 쉽다.

### 3단계: 접근법 제안

2-3가지 접근법을 제시한다. 각 접근법에 대해:

- **설명**: 어떤 방식인지
- **장점**: 왜 이 방식이 좋은지
- **단점**: 어떤 트레이드오프가 있는지
- **추천 여부**: 추천한다면 왜 추천하는지

추천하는 접근법을 먼저 제시하고 이유를 설명한다.

### 4단계: 설계 제시 및 승인

선택된 접근법을 기반으로 설계를 **섹션별로** 제시한다:

1. **아키텍처** — 전체 구조, 디렉토리 배치
2. **컴포넌트 설계** — 어떤 컴포넌트가 필요한지, 책임 분리
3. **데이터 흐름** — 상태 관리, API 연동, props 흐름
4. **에러 처리** — 에러 시나리오와 대응
5. **테스트 전략** — 어떤 테스트를 작성할지

각 섹션 제시 후 사용자에게 "이 부분 괜찮은지" 확인받는다. 복잡도에 따라 섹션을 줄이거나 합쳐도 된다. (간단한 기능이면 한 번에 제시해도 됨)

### 5단계: 설계 문서 저장

승인된 설계를 문서로 저장한다:

- 경로: `docs/plans/YYYY-MM-DD-<주제>.md`
- 형식:

```markdown
# <기능명> 설계

## 개요

(한 줄 요약)

## 배경

(왜 이 기능이 필요한지)

## 설계

### 아키텍처

(구조 설명)

### 컴포넌트

(컴포넌트 목록과 책임)

### 데이터 흐름

(상태/데이터 흐름)

### 에러 처리

(에러 시나리오)

## 구현 참고

(사용할 라이브러리, 기존 코드 활용 등)
```

### 6단계: 구현 전환

설계 문서 저장 후:

- 사용자에게 바로 구현을 시작할지 물어본다
- 구현 시작 시 설계 문서를 참조하며 작업한다
- 필요에 따라 `/feature`, `/component`, `/hook` 등 기존 커맨드를 활용한다

## 주의사항

- "이건 너무 간단해서 설계가 필요 없다"는 생각은 금지. 간단한 기능이면 설계도 간단하게 하면 된다.
- 사용자가 이미 명확한 요구사항을 가지고 있다면 질문 단계를 줄여도 된다.
- 설계가 확정되기 전까지 절대 코드를 작성하지 않는다.
