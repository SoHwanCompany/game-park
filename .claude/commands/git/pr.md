# /pr - Pull Request 작성

현재 브랜치의 변경사항을 분석하고 PR을 생성합니다.

> **참조**: `.claude/pr-rules.md`, `.github/pull_request_template.md`

## 작성 원칙

1. **Why 중심**: "무엇을 했는지"보다 "왜 필요한지"를 먼저 설명
2. **구체적으로**: placeholder 문구 남기지 않고 실제 내용으로 채움
3. **테스트 가능하게**: 리뷰어가 그대로 따라하면 검증할 수 있는 수준으로 작성
4. **해당 없음 명시**: 변경이 없는 섹션은 `해당 없음` 또는 삭제

## PR 제목

커밋 메시지와 동일한 형식: `[level] 설명`

예시:

- `[feat] 장바구니 기능 구현`
- `[bugfix] 헤더 스크롤 버그 수정`
- `[refactor] 인증 로직 리팩터링`

## 실행

1. 현재 브랜치와 develop 간 차이 확인 (`git log`, `git diff develop...HEAD`)
2. **모든 커밋 분석** (최신 커밋만이 아닌 전체)
3. PR 제목 작성 (`[level] 설명`)
4. PR 본문 작성 (아래 템플릿 준수)
5. `gh pr create --base develop` 실행

## PR 본문 템플릿

```markdown
## Why (변경 이유)

<!-- 이 PR이 필요한 이유. 어떤 문제를 해결하는지 -->

## What (변경 내용)

- 변경 사항 1
- 변경 사항 2

## How to Test (테스트 방법)

1. 검증 단계 1
2. 검증 단계 2

## Checklist

- [ ] 코드 컨벤션 준수
- [ ] 기능 정상 동작 확인
- [ ] 관련 Storybook 업데이트 (해당 시)

## Screenshots (스크린샷)

<!-- UI 변경 시 첨부. 없으면 "해당 없음" -->

해당 없음

## Related Issues (관련 이슈)

<!-- 관련 이슈가 있으면 링크. 없으면 삭제 -->
```

## 포맷팅 규칙

- 명령어, 파일명, 환경변수는 백틱으로 감싸기: `pnpm dev`, `NEXT_PUBLIC_API_URL`
- 변경 파일이 많으면 카테고리별로 그룹핑

## 주의사항

- 푸시되지 않은 커밋이 있으면 먼저 푸시
- 리모트 브랜치가 없으면 `-u` 플래그로 생성
- 베이스 브랜치는 `develop`
